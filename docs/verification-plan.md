## 1. 目的与范围

范围内：

- 在全矩阵（三个平台的 amd64，第 3.1 节）的隔离虚拟机上验证 FR-01～FR-14、NFR-01～NFR-08 的验收条件；arm64 的参考矩阵按需运行，结果只作参考（需求 D26）；
- 发布资产的完整性；
- 定义真实主机验收的内容。真实主机验收需要用户另行授权，本计划不授权执行。

范围外：

- 性能测量；
- vps-proxy-setup 自身的行为。测试只按需求第 7.2 节的约定模拟安装 3X-UI，用来验证共存；
- 云服务商的安全组（R-8），只在真实主机验收中记录。

## 2. 证据层次

| 层次 | 能证明 | 不能证明 |
|---|---|---|
| 静态检查 | 脚本语法、常见缺陷；仓库中没有秘密 | 运行行为 |
| 虚拟机生命周期 | 在官方云镜像上的端到端行为、重启后的状态、经虚拟网络的可达性 | 真实服务商的网络、镜像定制和控制台 |
| 公开发布回验 | 公开下载的资产与摘要一致 | 运行行为 |
| 真实主机验收 | 真实服务商环境下的行为 | 其他服务商的环境 |

报告时只陈述实际达到的最高层次，较低层次的证据不能代替较高层次。

## 3. 测试环境

### 3.1 平台矩阵

| 范围 | 组合 | 用途 |
|---|---|---|
| 全矩阵 | Debian 12、Debian 13、Ubuntu 24.04 的 amd64，共 3 组 | 与平台相关的行为：软件包、systemd、sshd、内核、重启 |
| 参考矩阵 | 上述三个平台的 arm64，共 3 组 | 在 aarch64 上重复全矩阵的用例。按需手动运行，发布前至少一次；结果只作参考，不作为里程碑出口（需求 D26） |
| 三平台 | 上述三个平台的 amd64 各一组 | 与架构无关的判定逻辑：输入校验、存量判定、漂移、端口变更、幂等 |

- 复用 vps-tuning 的做法：amd64 在 `ubuntu-24.04` 运行器上，arm64 在原生的 `ubuntu-24.04-arm` 运行器上；有 `/dev/kvm` 时用 KVM，否则用 TCG。
- 拉取请求和推送只运行全矩阵和三平台的作业；参考矩阵在手动触发时运行。M1、M2 期间 arm64 随每次运行执行，结果见详细设计第 8.1 节和附录 A。
- 镜像使用官方云镜像，按固定的 URL 和摘要下载（与 vps-tuning 的 `tests/platform-images.json` 同源）。
- 测试时会从官方仓库安装软件包，结果取决于当时的仓库状态。每次运行都记录实际安装的软件包版本。
- 每个作业的时长目标是 45 分钟以内（与 vps-tuning 相同），超出就拆分作业。M1 实测：amd64 作业约 2～4 分钟，arm64（TCG）约 10～12 分钟（详细设计第 8.1 节）；M2 实测：amd64 作业约 3～6 分钟，arm64 最长约 39 分钟（详细设计第 8.5 节、附录 A）。

### 3.2 客体初始状态

主配置是一台"典型最坏情况的新机"。所有条件都由 cloud-init user-data 显式写入，不依赖镜像的默认行为：

- root 可以用密钥登录，并设有 root 密码（用来验证密码登录确实被拒绝）；
- 镜像默认用户（Debian 为 `debian`，Ubuntu 为 `ubuntu`）有密钥，并有免密 sudo；
- `sshd_config.d/50-cloud-init.conf` 写有 `PasswordAuthentication yes`。

存量主机配置用于 FR-02 的拒绝用例，在主配置之上分别再加一项：

| 编号 | 附加条件 |
|---|---|
| S1 | 已按第 3.5 节安装 3X-UI |
| S2 | UFW 已启用，并有自定义规则。启用之前，在 UFW 未启用时依次检查两种情形（需求 D34）：IPv4 的 `before.rules` 中加了一条放行规则（在私有挂载命名空间中覆盖，真实文件不变）；已添加一条只放行 IPv6 的规则 |
| S3 | `jail.d` 中有一个自定义 jail |
| S4 | 已安装发行版的 `docker.io` |

每个会破坏状态的用例都运行在独立的 qcow2 覆盖层镜像上，互不影响。

### 3.3 网络与测试来源

| 来源 | 实现 | 用途 |
|---|---|---|
| 测试驱动 | 运行器经 QEMU 用户网络的端口转发连到客体：22、面板端口 2053、443、2096、80，以及一个未声明的端口 8080 | 外部可达性、正常登录、隧道、连续探测 |
| 第二来源 | 客体内的独立网络命名空间，经 veth 接口连接；IPv4 使用 `192.0.2.0/24`（RFC 5737），IPv6 使用 `2001:db8::/32`（RFC 3849） | 失败登录、Fail2ban 真实触发、IPv6 规则检查 |

- 经端口转发进入客体的连接，源地址是 QEMU 用户网络的网关地址 `10.0.2.2`，而不是回环地址，所以受 UFW 约束（已核实，M1 的 CI 证据，见详细设计第 8.2 节）。
- 经 veth 进入的流量走正常的入站路径，受 UFW 和 Fail2ban 约束。它证明的是规则本身，不是互联网路径；互联网路径由真实主机验收覆盖。
- 外部 IPv6 路径不依赖 QEMU 的端口转发。IPv6 规则在第二来源上检查，真实的外部 IPv6 路径留给 M5。
- 所有故意制造的失败登录都从第二来源发起，避免封掉测试驱动自己的来源。
- **Debian 13 的 `PerSourcePenalties`。** OpenSSH 9.8 起，sshd 会惩罚认证失败或不认证就断开的来源（需求第 10.1 节）。所以测试驱动的连续探测不能高频地"连上就断开"。探测方式和间隔已在 M1 实测确定（VO-2）：用密钥登录探测，间隔不小于 2 秒（详细设计第 8.2 节）；每次运行都归档 sshd 的惩罚日志，用来排除干扰。

### 3.4 测试密钥与秘密

- 每次运行由测试驱动在运行器上生成临时的 Ed25519 和 RSA 密钥对。用户实际使用 RSA 密钥，所以两种都要覆盖。生成密钥的是测试驱动，不是本工具（NFR-01 约束的是本工具）。
- 每次运行生成一个随机的测试密码，设为 root 密码，用来验证密码登录被拒绝。它同时是泄露扫描的标记字符串。
- 测试驱动记录自己的输入时，不写入密码。
- 测试只使用文档保留地址，不出现真实地址。

### 4.1 预检与输入（FR-01、FR-02、需求第 6 节）

| 编号 | 需求 | 场景 | 通过判据 | 范围 | 里程碑 |
|---|---|---|---|---|---|
| VT-01 | FR-01 | 在主配置上执行 `preflight`；另放置 `/var/run/reboot-required`，不声明公开端口再执行一次（需求 D41、D43） | 退出码为 0；执行前后状态摘要一致；放置待重启标记时只报警告 `reboot.required`，`inputs.open` 通过 | 全矩阵 | M1 |
| VT-02 | FR-01、FR-03、FR-04 | 分别制造不满足的前提：不是 root；`/etc/os-release` 改成不支持的版本；root 没有可用公钥（`authorized_keys` 没有公钥，或只有带 `command=` 的行）；包管理器被占用；sshd 的主配置末尾有 `Match Address` 块（块内 `PasswordAuthentication yes`），或排在本工具片段之后的片段中有同样的块（需求 D36）；同样的块写在 `Include` 所指的文件中，路径含空格，用双引号括起或用反斜杠转义空格，或者块以带引号的关键字 `"Match"` 开头，同时主配置中片段目录的 `Include` 带引号（需求 D40） | 输出具体原因，退出码非零；`preflight` 和 `apply` 都不改变系统。写法不同的块中另设各不相同的 `MaxAuthTries` 作为标记（被测主机在加固前就允许密码登录，`passwordauthentication` 不能说明块是否生效）：`sshd -T -C` 对块中的来源给出各自的标记值，对假定的连接不给出，即 sshd 应用了这些块；`sshd.match` 不符合，只列出含 `Match` 块的文件；带引号的片段 `Include` 不影响 `sshd.include` 通过 | 三平台 | M1 |

### 4.2 应用与认证（FR-03～FR-07）

| 编号 | 需求 | 场景 | 通过判据 | 范围 | 里程碑 |
|---|---|---|---|---|---|
| VT-10 | FR-05 | 主流程：经伪终端 `apply` → 用 root 的密钥开新会话 → `vps-hardening confirm` | 状态变为"已应用"；临时定时器和开机兜底单元都已撤除；随后 `verify` 通过 | 全矩阵 | M2 |

## 5. 真实主机验收（M5）

真实主机验收需要用户另行授权。以下只是验收内容，不是操作手册：

- **前提：** 使用一台新开的、非生产的 VPS；确认服务商控制台可用；能做快照时先做快照。服务商名称和真实地址只记在私有记录中，不进仓库。
- **流程：** 按需求 D42 更新系统、安装基础工具并重启 → 预检 → 应用（不声明公开端口，需求 D41）→ 在 Windows 11 上新开 PowerShell 会话完成确认 → `verify` → 从 Windows 探测 22、443、2096、2053、80 的可达性（只有 22 不被 UFW 拦截）→ 重启 → `verify` → 按 vps-proxy-setup 的约定安装 3X-UI → 用 `ports` 开放 3X-UI 的端口，在新的 PowerShell 会话中确认 → `verify` → 再次探测这 5 个端口（22、443、2096 不被拦截，2053、80 被拦截）→ 用用户的隧道命令访问面板 → 重启 → `verify`。
- **Fail2ban 真实触发：** 只在有一次性测试来源时做（例如另一台临时 VPS），不从管理员的出口触发（R-3，会被封 1 天）。没有一次性来源时，这一项以虚拟机证据（VT-33）为准，并在报告中写明。
- **云端安全组：** 记录安全组和防火墙的设置，与 UFW 的规则对照（R-8）。

## 6. 证据与记录

- **每个作业归档：** 工具输出、`verify` 输出、执行前后的状态摘要、软件包版本、镜像的 URL 和摘要、每次重启前后的 boot ID、连续探测日志、sshd 和 Fail2ban 的 journal 摘录（包括惩罚日志）、各阶段耗时。归档本身记录大小和 SHA-256（沿用 vps-tuning）。
- **上传前扫描：** 用测试密码等测试秘密扫描全部归档，包括串口日志；套件失败时同样扫描，命中即作业失败（需求 D55）。命中时归档仍会上传，便于定位；测试秘密每次运行随机生成，客体随作业结束（需求 D54）。
- **判定依据：** 按归档证据逐项判定，不以 CI 显示绿色为准（沿用 vps-tuning 的做法）。
- **失败分类：**
  - 环境失败（如下载失败、运行器故障）可以重跑，记录中要注明；
  - 与产品相关的偶发失败，重跑通过不算通过，找到原因之前一律记为失败。

## 8. 风险与限制

| 编号 | 风险或限制 | 影响 | 应对 |
|---|---|---|---|
| VR-1 | 虚拟机与真实 VPS 不同：virtio 设备、cloud-init 数据源、服务商对镜像的定制 | 虚拟机通过，真实主机仍可能失败 | M5 真实主机验收；预检对镜像差异保持保守 |
| VR-2 | arm64 运行器上可能没有 KVM，只能用 TCG，速度慢 | 作业超时 | M1 测量耗时，必要时拆分作业；M2 起 arm64 改为按需运行的参考矩阵（需求 D26），不再拖长拉取请求的测试 |
| VR-3 | 测试时的仓库状态与发布时不同 | 结果随时间漂移 | 记录软件包版本；发布前重跑全矩阵和参考矩阵 |
| VR-4 | Debian 13 的 `PerSourcePenalties` 干扰探测和登录用例 | 误报锁死或误报失败 | 失败登录只从第二来源发起；探测方式在 M1 实测确定；归档惩罚日志 |
| VR-5 | QEMU 用户网络对源地址和 IPv6 的支持有限 | 外部 IPv6 路径在虚拟机中测不到 | IPv6 规则在第二来源上检查；外部 IPv6 路径留给 M5 |
| VR-6 | 3X-UI 夹具依赖从 GitHub 下载 | 下载失败导致作业失败 | 固定摘要；下载失败记为环境失败 |
| VR-7 | 超时用例至少要等 3 分钟 | 增加 CI 时长 | 作业并行 |
| VR-8 | 测试驱动本身有缺陷 | 误判 | 用已知结果的对象自检，例如探测一个已知关闭的端口 |
